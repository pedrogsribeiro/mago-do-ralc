# EAP — Conclusão do M20 Player-Faced por Subsistemas do Storyteller

## 1. Objetivo e regra de condução

Esta EAP organiza a conclusão do projeto **M20 Player-Faced Total** a partir da visão operacional do Storyteller.

O objetivo não é decompor o trabalho em microfamílias matemáticas independentes. O projeto deve ser fechado **subsistema por subsistema**, conforme o Mestre reconhece e usa cada elemento em mesa: pessoas comuns, animais, criações tecnocráticas, Despertos, outras criaturas sobrenaturais, espíritos, obstáculos mundanos, riscos ambientais, veículos, hacking/Teia Digital e procedimentos dramáticos especiais.

O contrato normativo permanece o de `contrato_produto_player_faced_total.md`:

- o Storyteller rola zero dados;
- a experiência operacional do PJ permanece M20;
- nenhuma nova rolagem é transferida ou criada para o jogador apenas para absorver uma antiga rolagem do ST;
- o **Perfil DRP** é a linguagem comum para resistência do Obstáculo/NPC quando pertinente;
- ações próprias de NPCs/Obstáculos usam valores player-faced pré-convertidos quando substituem rolagens do ST;
- Persistência, recursos, estados, poderes e características específicas permanecem separados quando o M20 já os distingue;
- matemática serve à auditoria da transformação e só é aberta quando um procedimento concreto do subsistema exigir calibração.

### Regra de fluxo

**Somente um pacote de trabalho operacional pode estar ativo por vez.**

Dentro de cada pacote:

1. levantar o procedimento original do M20 e o corpus canônico correspondente;
2. aplicar às fichas as transformações matemáticas já estabelecidas pelo projeto;
3. converter **cada perfil canônico** daquele subsistema para o novo formato DRP;
4. preservar Persistência, Recursos, Características e procedimentos especiais que não pertencem ao DRP;
5. registrar como dívida do **método**, e não como bloqueio de cada NPC, limitações estatísticas já conhecidas da compressão;
6. abrir cálculo/script novo **somente** quando aparecer uma mecânica que ainda não possua transformação definida;
7. homologar o pacote convertido;
8. só então abrir o pacote seguinte.

A conversão de um NPC comum não exige uma nova simulação apenas porque seus números são diferentes. A matemática já existente é a régua de transformação.

Não iniciar um subsistema novo porque ele apareceu incidentalmente durante outro. Registrar a dependência e manter o foco.

---

# 2. Definição de pronto de qualquer subsistema

Um subsistema só pode ser marcado como concluído quando:

- [ ] o procedimento original relevante do M20 foi identificado;
- [ ] a experiência do jogador permaneceu operacionalmente igual;
- [ ] nenhuma rolagem do Storyteller permaneceu escondida no procedimento;
- [ ] o Perfil DRP ou outra representação player-faced adequada foi definido;
- [ ] ações próprias do NPC/Obstáculo foram convertidas quando necessárias;
- [ ] Persistência/recursos/estados originais foram preservados quando pertinentes;
- [ ] poderes e exceções concretas foram representados sem serem dissolvidos em um número genérico;
- [ ] cada NPC/entidade/perfil canônico daquele subsistema recebeu sua própria versão player-faced;
- [ ] exemplos de mesa suficientes confirmam que o ST consegue usar a ficha sem reconstruir a ficha M20;
- [ ] dívidas remanescentes foram registradas explicitamente;
- [ ] a homologação autoral foi registrada antes de qualquer propagação editorial ampla.

# 3. Estado já consolidado antes desta EAP

## 3.1 Contrato e linguagem comum

- [x] Contrato Player-Faced Total estabelecido.
- [x] Zero rolagens do Storyteller como invariante.
- [x] Preservação integral da experiência operacional do PJ como invariante.
- [x] Perfil DRP homologado como gramática comum.
- [x] Representação esparsa/progressiva homologada: `6`, `6/2`, `6/2/1`.
- [x] Dimensões previstas: Físico, Social, Mental/Técnico, Mágicko/Poderes.

- [x] Eixos Passivo/Ativo, Simples/Elaborado e Pontual/Persistente/Alto impacto preservados como classificações independentes.

## 3.2 Matemática que já pode ser reutilizada

- [x] Oposição ativa D/R possui baseline experimental utilizável.
- [x] Proteção física derivada de soak possui baseline operacional.
- [x] Composição física PJ → NPC por D/R/P foi auditada.
- [x] Armas de fogo do PJ preservam sua dificuldade própria e consultam apenas os componentes pertinentes.
- [x] Transposição universal de D/R para dificuldades próprias foi rejeitada.
- [x] Ações físicas do NPC possuem procedimento de conversão por sucessos fixos e efeito-base já suficiente para conversão de fichas; limitações residuais permanecem documentadas no nível do método.
- [x] Social resistido foi estudado o suficiente para abandonar a busca de fórmula universal.
- [x] Força de Vontade não deve ser convertida genericamente em Proteção Social.
- [x] `P Social = 0` é o default de trabalho até que um procedimento original concreto demonstre uma camada quantitativa posterior equivalente a Proteção.

## 3.3 Dívidas conhecidas que não devem ser abertas fora de contexto

Estas dívidas só serão tratadas quando bloquearem o subsistema ativo:

- ataque/dano de NPC sem defesa/reação original do PJ;
- mágika hostil unilateral;
- contramágika;
- Reação de Paradoxo;
- Fúria/Gnose de espíritos;
- iniciativa foi resolvida para NPCs por valor fixo derivado de Destreza + Raciocínio + 6; a ficha final mostra apenas o valor pronto;
- Certámen;
- efeitos especiais que dependam de procedimentos próprios.

# 5. Inventário canônico de NPCs/Entidades — regra de não esquecimento

A existência de uma ficha pronta no livro é suficiente para gerar uma obrigação de produto:

> **cada perfil canônico de NPC/entidade que o M20 oferece ao Storyteller deve receber uma versão correspondente no modelo player-faced, salvo exclusão autoral explícita.**

Portanto, cada pacote de atores começa com uma tarefa obrigatória de **inventário contra a fonte primária**.

O inventário atualmente consolidado no repositório é apenas o ponto de partida. Ele não deve ser tratado como prova de exaustividade do livro.

Para cada perfil convertido, registrar no mínimo:

- [ ] nome/categoria;
- [ ] descrição diegética;
- [ ] Perfil DRP genérico ou por dimensão;
- [ ] ações próprias com S/efeito quando necessárias;
- [ ] Persistência/Vitalidade/Essência/Structure pertinente;
- [ ] equipamentos;
- [ ] poderes/características;
- [ ] estados e gatilhos;
- [ ] fonte M20 usada na conversão;
- [ ] observações de equivalência;
- [ ] dívidas abertas, se houver.

# 6. Pacote de consolidação depois dos subsistemas

## PT-12 — Catálogo DRP e tabela empírica de referência

**Pré-requisito:** os pacotes de atores devem possuir amostra convertida suficiente.

- [ ] reunir todos os Perfis DRP homologados;
- [ ] reunir todas as ações S + efeito homologadas;
- [ ] observar recorrências reais;
- [ ] estudar clusters/faixas de competência via script;
- [ ] derivar, se os dados sustentarem, referências ergonômicas de construção rápida inspiradas apenas na ideia de tabelas de referência por potência;
- [ ] não definir tiers, nomes, cortes ou números antes dos dados;
- [ ] testar monotonicidade e cobertura do corpus;
- [ ] manter perfis excepcionais como exceções, sem forçá-los a uma escala única.

Resultado esperado: ferramenta de criação rápida para o ST baseada nos NPCs efetivamente convertidos.
