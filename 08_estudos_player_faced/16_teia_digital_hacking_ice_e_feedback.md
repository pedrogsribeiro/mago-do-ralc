# Estudo 16: Teia Digital, Hacking, ICE e Feedback

Este estudo trata o domínio de **hacking e confrontos virtuais** em M20.

A bíblia atual fornece quatro bases claras:

1. hacking de servidor pode ser um **teste estendido**;
2. disputas virtuais complexas podem ser **estendidas-resistidas**;
3. ataques lógicos usam **Computação + Arete**;
4. falhas graves ou dano virtual podem produzir **feedback Letal** no corpo físico do hacker.

O corpus, porém, **não contém um procedimento detalhado e consolidado de ICE**, com ficha, pools, ações, dano e estados suficientes para uma tradução universal.

Portanto, este estudo separa o que já pode ser tratado com segurança do que ainda depende de recuperação da regra original.

---

## 1. Gate de fidelidade

A experiência do jogador precisa preservar:

* Computação;
* Arete;
* canais de Correspondência/Dados quando aplicáveis;
* Quintessência;
* testes estendidos;
* testes resistidos;
* economia de ações;
* risco de feedback;
* consequências físicas reais;
* diferenças entre servidor passivo, operador ativo e ICE.

A camada player-facing não deve:

* transformar todo hacking em uma única rolagem;
* substituir Computação + Arete por um atributo genérico;
* inventar “vida de servidor” universal;
* criar ICE sem base nas regras originais;
* remover feedback físico apenas para simplificar.

---

## 2. Hacking passivo: já quase player-facing

Quando o personagem invade um sistema que não possui oposição ativa própria, M20 já oferece uma estrutura fortemente compatível com player-facing:

```
PJ rola
→ acumula sucessos
→ alcança o total necessário
```

A própria bíblia usa como exemplo:

> hackear um servidor corporativo pode exigir vários sucessos acumulados.

Isso se encaixa diretamente em **Integridade/Relógio como interface de progresso**, desde que o relógio represente exatamente o número de sucessos que a tarefa original exige.

Exemplo:

```
SERVIDOR CORPORATIVO

Progresso necessário: 15

PJ:
Computação + habilidade pertinente
ou Computação + Arete quando a regra mágicka exigir

1 sucesso:
+1 Progresso

2 sucessos:
+2 Progresso

3 sucessos:
+3 Progresso
```

### Gate

**PASSA SEM CONVERSÃO DO MOTOR.**

O Relógio é apenas visualização de um teste estendido já existente.

---

## 3. Oposição ativa

Quando existe um agente real tentando impedir a invasão:

* operador humano;
* hacker rival;
* entidade consciente;
* sistema que possua procedimento explícito de oposição;

a situação deixa de ser apenas tarefa estendida.

Se a regra original for **resistida** ou **estendida-resistida**, a competência adversária pode alimentar **Oposição**.

A conversão deve partir da parada real do oponente, nunca de um “nível de segurança” genérico inventado.

### Gate

**PASSA PELA ARQUITETURA DE OPOSIÇÃO.**

A matemática é a mesma família dos Estudos 02/05.

---

## 4. Sistemas sem agência

Um servidor passivo, firewall estático ou barreira lógica não precisa ser tratado como NPC.

Pode possuir:

* dificuldade;
* total de sucessos exigido;
* estados;
* gatilhos;
* consequências;
* proteção adicional;
* credenciais que alteram condições.

Exemplo:

```
SERVIDOR DE SEGURANÇA

Estado:
normal

Progresso:
0 / 10

Gatilhos:
3 sucessos acumulados → auditoria automática
6 sucessos → setor sensível exposto
10 sucessos → acesso completo
```

Esses gatilhos só devem existir se representarem comportamentos reais do sistema e não uma dramaturgia arbitrária.

### Gate

**PASSA COMO OBSTÁCULO SEM AGÊNCIA.**

---

## 5. Computação + Arete

A bíblia registra ataques virtuais com **Computação + Arete**.

Isso precisa permanecer reconhecível para o jogador.

A camada player-facing não substitui essa parada por:

* Mental/Técnico genérico;
* “hacking 7”;
* dificuldade universal;
* valor de dano virtual abstrato.

As dimensões da ficha achatada podem apenas indexar o procedimento:

```
Mental/Técnico:
- Computação + Arete
- Correspondência/Dados
- Quintessência
- oposição relevante
- estado do sistema
```

### Gate

**PRESERVAR.**

---

## 6. Feedback

A bíblia atual afirma que dano lógico severo ou falha crítica pode causar **dano Letal no corpo físico**.

Esse feedback é uma consequência real e não deve ser reduzido a “perde 1 progresso”.

Ele pertence ao campo **Consequência**.

Exemplo estrutural:

```
Consequência:
feedback Letal
```

Mas o estudo não fixa ainda um número universal de dano, porque o corpus atual não fornece uma tabela geral suficiente para isso.

### Gate

**PRESERVAR COMO CONSEQUÊNCIA FÍSICA.**

---

## 7. Botch

Falha crítica em hacking/combate virtual continua sendo botch segundo M20.

Ela pode:

* interromper invasão;
* expor identidade;
* acionar rastreamento;
* danificar equipamento;
* gerar feedback;
* abrir acesso ao oponente;
* produzir outra consequência suportada pela regra específica.

O produto final deve preservar a diferença entre:

* falha simples;
* botch;
* dano/feedback.

### Gate

**PRESERVAR.**

---

## 8. ICE

A bíblia atual menciona Teia Digital, hacking e feedback, mas não fornece ainda uma ficha/procedimento completo e consolidado de ICE.

Logo, este estudo **não pode homologar**:

* pool padrão de ataque de ICE;
* pool padrão de defesa;
* dano padrão;
* Integridade padrão;
* Limiar padrão;
* estados universais;
* algoritmo de perseguição virtual.

### O que já podemos afirmar

Se um ICE específico tiver:

* agência;
* ações próprias;
* pools;
* recursos;
* estados;

ele deve ser tratado como **constructo-agente**.

Se for apenas uma barreira/protocolo:

* é **sistema ativo ou passivo**, não NPC.

### Gate

**LACUNA DOCUMENTAL.**

É preciso recuperar as regras originais de ICE antes de fechar a tradução comercial.

---

## 9. Hacking como conflito persistente

Quando a invasão possui progressão prolongada, a ficha achatada pode usar:

| Campo | Aplicação |
| :--- | :--- |
| Oposição | operador/ICE ativo que resiste |
| Ameaça | contra-ataque/rastreamento ativo |
| Consequência | bloqueio, exposição, feedback |
| Integridade/Relógio | sucessos ainda necessários |
| Limiar | proteção real que reduza Impacto, se a regra original fornecer equivalente |

### Regra de 1 sucesso

Se existe Relógio:

> **1 sucesso continua sendo sucesso marginal e normalmente reduz 1 caixa**, além de mover a ficção.

O ST pode qualificar o avanço:

* acesso parcial;
* credencial temporária;
* vazamento de metadados;
* abertura de uma camada;
* exposição limitada.

Mas o sucesso não vira “só complicação”.

---

## 10. Estados digitais

A Teia Digital é particularmente adequada para estados.

Exemplos possíveis, desde que suportados pelo sistema concreto:

* não detectado;
* detectado;
* rastreado;
* credencial comprometida;
* acesso parcial;
* acesso privilegiado;
* sistema isolado;
* conexão cortada.

Esses estados podem alterar quais ações existem sem exigir HP fictício.

### Gate

**PASSA COMO LINGUAGEM DE REPRESENTAÇÃO.**

---

## 11. Telegrafia

A lógica de telegrafia pode aparecer quando há escalada legível:

```
intrusão detectada
→ rastreamento iniciado
→ origem localizada
→ contramedida/feedback
```

Cada etapa pode ter efeito real.

Isso funciona especialmente bem quando o sistema original já possuir:

* detecção;
* rastreamento;
* isolamento;
* contra-ataque.

Não se deve inventar etapas apenas para criar suspense.

---

## 12. Matriz de decisão

| Situação | Tratamento |
| :--- | :--- |
| Hacking simples | teste do PJ |
| Hacking prolongado | teste estendido / Relógio equivalente |
| Operador rival | Oposição ativa |
| Disputa prolongada | estendida-resistida |
| Computação + Arete | preservar |
| Quintessência | preservar |
| Servidor passivo | Obstáculo sem agência |
| Firewall estático | dificuldade/progresso, conforme regra original |
| Feedback | Consequência física |
| Botch | preservar |
| ICE agente | constructo-agente, se a ficha original sustentar |
| ICE barreira | sistema/barreira |
| ICE genérico sem regra consolidada | não inventar |

---

## 13. Gate do Estudo 16

O domínio passa parcialmente.

### Resolvido

* hacking simples;
* hacking estendido;
* relógio como visualização de sucessos acumulados;
* oposição ativa quando existe agente real;
* preservação de Computação + Arete;
* Quintessência;
* feedback como Consequência;
* estados digitais;
* telegrafia quando houver escalada causal.

### Lacuna

* procedimento completo de ICE;
* valores de ataque/defesa/dano de ICE;
* tradução específica de combate virtual detalhado;
* calibração de consequências quando o corpus original fornecer pools próprios.
